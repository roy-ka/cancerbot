# CancerBot TODO

## Critical
- [x] **Rate limiting on register and forgot-password** — `/auth/register/` and `/auth/forgot-password/` have no abuse protection; add per-IP or per-email rate limiting consistent with the `LoginAttempt` pattern already used for login
- [x] **JWT token revocation on password change** — tokens are 60,000-minute JWTs with no invalidation list; resetting or changing password should invalidate all existing sessions
- [x] **Token budget check + fallback** — catches `groq.GroqError` and retries with OpenAI (`gpt-4o-mini` by default); both providers failing raises a clear error; controlled by `OPENAI_API_KEY` and `OPENAI_FALLBACK_MODEL`
- [x] **Retry logic for external APIs** — `_retry_get` async helper with exponential backoff (1s → 2s + jitter) retries on 429/5xx and network/timeout errors; used by PubMed and CrossRef; `_wiki_search` has equivalent sync retry; 2 attempts, 8s timeout
- [x] **OpenSearch index cleanup** — sources chunked (150w/40w overlap) with source_id dedup; search deduped to 1 result per source_id; backfill script migrates existing docs using terms from PostgreSQL messages

## High
- [x] **Change password** — authenticated endpoint allowing users to update their password (current password + new password)
- [x] **Delete user** — email-confirmed deletion with a 7-day grace period: request email → confirm with password → scheduled deletion → login blocked/cancellable in the meantime → background sweep cascades and sends the farewell email
- [x] **Ninja user** — on startup, create a privileged "ninja" user from `NINJA_EMAIL`/`NINJA_PASSWORD` if it doesn't exist; ninja can browse all users, open any of their conversations, and post messages that get real answers but are flagged `hidden_from_user` and never surface to the real user (via `/ninja/*` routes, `src/routers/ninja.py`). Ninja JWTs are capped at 2h regardless of rememberMe.
- [x] **LLM response streaming** — WebSocket infrastructure already exists; stream Groq tokens incrementally instead of buffering the full response, significantly improving perceived latency

## Medium
- [x] **Conversation title auto-generation** — first message's title is regenerated via `OllamaConnector.generate_title` (short Groq call, heuristic fallback) after the answer is saved, not blocking the streamed response. `scripts/backfill_conversation_titles.py` regenerates existing conversations still on the naive prefix; runs automatically on deploy.
- [x] **Source recency scoring** — `pub_year` indexed (PubMed + CrossRef) and boosted in `src/retrieval/search.py` via `RECENT_BOOST` / `SEMI_RECENT_BOOST` `should` clauses
- [x] **Improve search using tags** — docs now carry `pub_year`, `pub_types`, `evidence_level` (derived from publication type via `EVIDENCE_LEVELS`) and `disease_areas` (from the NLP service's category map). Retrieval boosts high-evidence, recent, and disease-area-matching sources, and hard-excludes editorials/comments/errata/retractions. CrossRef now requests `type,subject,published`. **PubMed MeSH/publication-type query filters were deliberately skipped** — narrowing at fetch time risks breaking the AND-of-OR-groups query, so evidence is weighted at retrieval instead. Backfill: `scripts/backfill_source_metadata.py` (runs on deploy). Boost weights are unmeasured heuristics — tune the constants at the top of `search.py` once real query behaviour is observed
- [x] **Clinical trial search (evidence)** — ClinicalTrials.gov v2 API as a fourth automatic source (`_search_clinicaltrials_sources`), filtered to COMPLETED trials, indexed + cited like other sources via a new `nct:` stable id. Content = title + Conditions/Interventions/Phase/Status + summary; completed-with-results → evidence level 3, else default. Shares `_build_boolean_term_query` with PubMed
- [x] **Distinguish clinical-trial sources in the UI** — trial citations now render as a distinct outlined "Trial · Phase · Status" `Chip` (Biotech icon, secondary color) in `MessageSourceItem`, instead of the plain paper citation style. The backend (`_hit_to_entry` in `src/db/repositories/messeges.py`) surfaces the trial title as the display `name` (not the raw `nct:` id) and parses `phase`/`status` out of the trial's own `full_text` facts line (`Phase: … | Status: …`, written in `conversation_helper.py`) — **no reindex/backfill needed**, since `sources` is serialized as a raw dict and we control that format. Phase/status prettified client-side (`client/src/utils/trialBadge.ts`, e.g. `PHASE2`→`Phase 2`). Trade-off: parsing couples to that facts-line format; promoting `phase`/`status` to real indexed fields is the cleaner long-term path if other features need them
- [ ] **Clinical trial participation ("find trials I could join")** — a *separate, opt-in* feature (not the automatic per-message search): user enters a coarse location (city/country, not GPS), and we deep-link to ClinicalTrials.gov's own recruiting search pre-filled with condition + location. Keeps the authoritative source authoritative and avoids presenting enrollment guidance as vetted medical advice (CancerBot is advisory-only). A richer fetch-and-render version can follow if the deep-link proves too thin
- [x] **Wikipedia HTTP connection pooling** — `_search_wikipedia_sources._fetch()` now opens one `httpx.Client` and passes it to every `_wiki_search` call (optional `client=` param, falls back to module-level `httpx.get`), so the per-term search calls share one keep-alive connection instead of a TLS handshake each. Note: the `_wiki.page()` fetches still use `wikipediaapi`'s own urllib client and aren't poolable through this — a deeper change if that overhead ever matters

- [x] **Split name into first and last** — `User.name` replaced with `first_name` + `last_name` (both required at registration; `User.display_name` property for single-string uses). Migration `split_user_name_001` backfills existing rows by splitting on the first space, then drops `name`. Registration form has two fields; `/auth/check/` and `/ninja/users/` return both. Emails greet with the full name via `display_name` (SendGrid `{{name}}` templates unchanged — they receive the full name). Verified live: migration ran on the dev DB (`"roy ka"`→`('roy','ka')`) and an end-to-end UI registration persisted `('Grace','Hopper')`

- [x] **Rate limiting on `/auth/request-delete/`** — throttled per user (`request-delete:{user_id}`, `MAX_REQUEST_DELETE_ATTEMPTS=5`, 60-min block) using the existing `RateLimitEntry` machinery, mirroring `/auth/forgot-password/`. Keyed by user id (endpoint is authenticated) rather than an attacker-supplied value, so it's naturally bounded and covered by the existing stale-entry sweep
- [ ] **Pending-deletion logout has no explanation** — when `get_current_user` rejects a session because deletion was scheduled from another device, the user is silently bounced to `/login` with no message; the "cancel deletion" dialog only appears after resubmitting the login form. Surface this via a query param/toast on the redirect instead
- [x] **Tokenized links logged to Axiom in non-prod** — the three non-prod link logs (verification, password reset, delete-account request — the TODO undercounted at two) now pass through `_redact_token()`, masking the `token=` query value to `***`. Closes the leak where a staging deploy with `AXIOM_TOKEN`/`AXIOM_DATASET` set forwarded live reset/verification/deletion tokens to a third-party log store. The link path + recipient are still logged for dev visibility
- [ ] **Index `deletion_scheduled_at`** — the hourly account-deletion sweep (`src/jobs/account_deletion.py`) does a full sequential scan of `users`; add a partial index (`WHERE deletion_scheduled_at IS NOT NULL`) before the user base grows
- [ ] **Deletion-cancellation email** — `cancel_delete_account` (`src/routers/auth.py`) clears `deletion_scheduled_at` but sends no confirmation email; the request and scheduled-deletion steps both email the user, cancellation should too (new `EMAIL_TEMPLATES` entry + sender in `src/utils/email.py`)

## Bugs
- [x] **Delete conversation not visible** — the delete conversation action is not exposed in the UI; users have no way to delete a conversation from the frontend
- [x] **Fix sources in prod** — (2026-07-20, resolved 2026-07-22) root causes were in the query-building path, not the sources themselves: (1) entity synonyms were flattened into one bag so a heavily-synonymed term (5 GBM synonyms) drowned out a single-term one (a drug name) — now grouped per entity, with PubMed building AND-of-OR-groups; (2) the grouped extraction never actually ran, since `conversations.py` pre-cached flat `extracted_terms` on the current message and `search_and_embed`'s cache shortcut always hit first; (3) the final BM25/KNN retrieval query was itself built from the flat synonym-expanded list. Also added cancer-category grouping (GBM → brain cancer), `has-abstract:true` on CrossRef, and a `full_text_word_count >= 20` retrieval filter to exclude title-only sources
