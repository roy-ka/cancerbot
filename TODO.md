Deep-link rather than fetch-and-render keeps the authoritative source authoritative and avoids presenting enrollment guidance as vetted medical advice; the dialog states plainly that CancerBot does not screen eligibility. **Nothing is prefilled from the conversation** — guessing the user's diagnosis from chat text is exactly the wrong thing to get subtly wrong (there's an E2E asserting the fields stay empty). **No backend involvement at all**: the URL is built and opened client-side, so the condition/location never reach our backend or DB, and there's no new fetch/SSRF surface. - [ ] **Explain privacy to the user** — there is currently **no privacy explanation anywhere in the app**: only `/terms` exists (`client/src/pages/Terms.tsx`), and it says nothing about data handling. Users are typing health questions — often about their own diagnosis — with no statement of what is kept, for how long, or who can see it. Write a plain-language privacy explainer (its own `/privacy` route, linked from the login/register screens and the sidebar next to About) covering what the app actually does today, verified against the code rather than written aspirationally:
  - **Conversations are stored** in PostgreSQL (`messages`, `conversations`) and are *not* end-to-end encrypted; soft-deleted conversations remain in the DB
  - **A privileged ninja account can read any user's conversations** (`src/routers/ninja.py`) and post hidden messages into them — this is the most surprising item for a user and must be disclosed honestly
  - **Questions are sent to third parties**: message text goes to Groq (and Gemini on fallback) for generation, and NLP-extracted terms go to PubMed/CrossRef/Wikipedia/ClinicalTrials.gov as live search queries
  - **Logs go to Axiom** when configured (`AXIOM_TOKEN`/`AXIOM_DATASET`)
  - **What is not collected**: no GPS/precise location; the trial-participation dialog's condition/location never reach the backend (see the participation item above)
  - **Account deletion**: the 7-day grace period, what the sweep actually cascades, and how to cancel
  - Pairs with the onboarding item below — if we start storing cancer type/stage, this explainer becomes a prerequisite, not a nice-to-have
- [ ] **Onboarding: cancer type, stage and required data** — offer an onboarding step (after registration, and re-editable later from account settings) that collects the user's clinical context: cancer type / primary site, stage, and whatever else materially changes an answer (e.g. biomarkers/mutations such as EGFR/IDH/HER2, prior or current treatment lines, age band). Feed it into the query pipeline so answers are personalised without the user restating it every message — the natural hooks are the `disease_areas` boost already in `src/retrieval/search.py` and a short profile preamble in `OllamaConnector._build_prompt`. Open questions worth deciding explicitly before building:
  - **Optional and skippable.** This is sensitive health data about the user themselves, not a research query — it must never be a hard gate on using the app, and needs a clear "why we ask / how it's used" explanation plus easy edit and clear-out. Deletion must cascade with the existing account-deletion flow
  - **Storage.** New columns on `users` vs. a separate `user_profiles` table (preferred: keeps a sensitive, optional, evolving field set out of the auth-critical table)
  - **Scope of influence.** Whether the profile biases *retrieval* (boosts), only the *prompt*, or both — biasing retrieval risks hiding relevant general evidence, so starting prompt-only and measuring is the safer order
  - **Advisory-only framing.** CancerBot is advisory, so a stored stage/biomarker profile must not turn answers into individualised treatment recommendations; the existing disclaimer wording likely needs strengthening for profiled answers

- [x] **Fix sources in prod** — (2026-07-20, resolved 2026-07-22) root causes were in the query-building path, not the sources themselves: (1) entity synonyms were flattened into one bag so a heavily-synonymed term (5 GBM synonyms) drowned out a single-term one (a drug name) — now grouped per entity, with PubMed building AND-of-OR-groups; (2) the grouped extraction never actually ran, since `conversations.py` pre-cached flat `extracted_terms` on the current message and `search_and_embed`'s cache shortcut always hit first; (3) the final BM25/KNN retrieval query was itself built from the flat synonym-expanded list. Also added cancer-category grouping (GBM → brain cancer), `has-abstract:true` on CrossRef, and a `full_text_word_count >= 20` retrieval filter to exclude title-only sources
