Standing up a new CancerBot server, start to finish

Every command and cloud-console step needed to take a bare Hetzner Cloud server to a working https://cancer-bot.com deployment — in the order that avoids the dead ends we hit the first time. Run each code block on its own; don't paste multiple commands as one block.

01

Clone the repo and configure the environment

Standard setup — the only CancerBot-specific thing is how many .env values are Docker-network hostnames rather than localhost.

Clone and copy the env template

git clone https://github.com/roy-ka/cancerbot.git
cd cancerbot
cp example.env .env

Host prerequisites

Install these once: git, Docker with the compose plugin (docker compose version must work), and Node.js 20.19+ — deploy.sh builds the frontend on the host with npm, not in a container. Trivy is optional: if it's installed, deploy.sh scans the built images and aborts on fixable HIGH/CRITICAL findings; if not, it warns and skips the scan.

sudo apt-get install -y trivy   # optional — after adding Aqua's apt repo

Fill in .env

example.env documents every variable. For production, set at least:

ENV=production
FRONTEND_URL=https://cancer-bot.com          # origin used in every emailed link
CORS_ORIGINS=https://cancer-bot.com,https://www.cancer-bot.com
LLM_PROVIDER=groq                            # default is ollama — production uses Groq
GROQ_API_KEY=...
GROQ_MODEL_NAME=openai/gpt-oss-120b            # no quotes
JWT_SECRET=...                               # 32+ chars: python3 -c "import secrets; print(secrets.token_hex(32))"
POSTGRES_PASSWORD=...
OPENSEARCH_INITIAL_ADMIN_PASSWORD=...        # 8+ chars with upper, lower, digit and symbol
REDIS_PASSWORD=...
BREVO_API_KEY=...                            # required: every sign-in is a code sent by email

Optional: NINJA_EMAIL (admin console — it signs in with a code sent to that address, so it must be a real inbox; NINJA_PASSWORD is no longer used and can be removed), ADMIN_DIGEST_EMAILS (daily/weekly digests), UNPAYWALL_EMAIL, and the Axiom trio AXIOM_TOKEN_WRITE / AXIOM_TOKEN_READ / AXIOM_DATASET. OPENSEARCH_CA_CERT is set in Phase 6.

The containers don't need POSTGRES_URL, OPENSEARCH_URL, OLLAMA_URL, NLP_SERVICE_URL or REDIS_URL — the compose files give them the in-network values, and those override anything in .env. The only host-side values you add are the backup ones in Phase 9. Never set DEV_EMAIL_SHORTCUTS here.

The backend refuses to start when ENV is missing; ENV=production without FRONTEND_URL; the LLM settings are incomplete (LLM_PROVIDER unknown, or the chosen provider's key/model missing — with no LLM_PROVIDER it expects a local Ollama model); CORS_ORIGINS=*; DEV_EMAIL_SHORTCUTS set in production; JWT_SECRET shorter than 32 characters; or OpenSearch reached over plain http:// in production. The container log names the exact problem.
Learned the hard way A bad AXIOM_DATASET doesn't just disable logging — AxiomHandler.emit() calls flush() synchronously with no exception handling, so a rejected dataset name can raise straight up through any code path that logs anything. Get the dataset name right, or leave AXIOM_TOKEN_WRITE / AXIOM_DATASET empty.
02

Put a Hetzner Cloud Firewall in front of the server

A Hetzner Cloud server sits on a public IP with no firewall at all by default — every listening port is reachable from the internet. Two of ours must not be: Ollama (11434, bound to 0.0.0.0 in Phase 5, no authentication) and the backend (8000, published by Docker on 0.0.0.0, which would bypass nginx). Do this before the first deploy.

Create the firewall and attach it

Hetzner Console → your project → Firewalls → Create Firewall. Inbound rules, source Any IPv4 + Any IPv6:

  • TCP 22 (SSH — narrow the source to your own IP if it's stable)
  • TCP 80 and TCP 443
  • ICMP (optional, for ping)

Leave outbound empty (allows everything). Under Apply to, select this server, then create.

ufw alone is not enough Docker writes its own iptables rules for published ports, and they're evaluated before ufw's, so ufw deny 8000 does nothing for the backend. The Cloud Firewall filters before traffic reaches the server, so Docker can't get around it. Leave ufw inactive (the Hetzner Ubuntu default) unless you know you need it.

Check it from outside

From your own machine (not the server), once Ollama and the stack are up — both must time out:

curl -m 5 http://SERVER_IP:11434
curl -m 5 http://SERVER_IP:8000/health/
How to tell which layer is actually blocking you Port 80 timing out from outside almost always means the Cloud Firewall is missing the rule or isn't applied to this server. To confirm, start a throwaway listener (sudo python3 -m http.server 80) and curl the server's public IP from an outside machine. A silent timeout means a firewall is dropping packets before they reach the OS; "connection refused" means something OS-level rejected it. Kill the listener the moment the test is done — it serves a directory listing of the whole working directory, .ssh/ included.
03

Fix home-directory permissions for nginx

nginx serves the built frontend straight out of ~/cancerbot/client/dist (/root/cancerbot when you work as root, the Hetzner default), running as www-data. Ubuntu home directories default to 750 (and /root to 700), which blocks www-data from even traversing into them — no amount of chmod on client/dist itself fixes this.

# grants traversal only — doesn't make your home directory's contents listable
sudo chmod o+x ~
Diagnose with namei namei -om /path/to/client/dist/index.html prints the permission bits for every directory in the path in one shot — the fastest way to spot which parent is the blocker.
04

Install nginx and get the site's TLS certificate

Order matters here: scripts/setup-nginx.sh installs the repo's nginx.conf (with this checkout's path filled in as the web root), and that config already points at cert files that must exist first, so certbot has to run before it, standalone, before nginx is even listening on port 80.

Install nginx and certbot

sudo apt-get update
sudo apt-get install -y nginx certbot

DNS must point here first

Confirm the domain resolves to this server's public IP, not a CDN/proxy IP:

dig +short @1.1.1.1 cancer-bot.com
curl -s ifconfig.me   # compare against the dig output
If the domain is behind Cloudflare Switch the A record's proxy status to "DNS only" (grey cloud) before requesting the cert — while proxied, Let's Encrypt's HTTP-01 challenge has to round-trip through Cloudflare's edge to your origin, and any mismatch surfaces as an opaque 522. You can re-enable the proxy after the cert is issued.

Issue the certificate

sudo systemctl stop nginx   # frees port 80 for certbot's standalone server
sudo certbot certonly --standalone -d cancer-bot.com -d www.cancer-bot.com

Apply the nginx config and start it

sudo ./scripts/setup-nginx.sh
sudo systemctl start nginx   # setup-nginx.sh calls "reload", which no-ops if nginx isn't already running
05

Install Ollama on the host

Ollama isn't containerized in this stack — docker-compose.yml points the backend at 172.30.0.1:11434, the Docker bridge gateway IP, specifically so containers can reach a host-level process. The official installer binds Ollama to 127.0.0.1 only, which that gateway route can't reach.

curl -fsSL https://ollama.com/install.sh | sh
ollama pull nomic-embed-text

With LLM_PROVIDER=groq, Ollama only computes embeddings, so the server needs no chat model. Only if you run with LLM_PROVIDER=ollama do you also need ollama pull of the model named in OLLAMA_GEN_MODEL.

Rebind it to all interfaces

# opens an editor — add exactly these two lines, save, exit
sudo systemctl edit ollama
[Service]
Environment="OLLAMA_HOST=0.0.0.0"
sudo systemctl daemon-reload
sudo systemctl restart ollama
sudo ss -tlnp | grep 11434   # should now read 0.0.0.0:11434, not 127.0.0.1:11434
06

Generate OpenSearch's internal TLS certs

This is a separate certificate from the public site's — self-signed, scoped to the Docker network, and required before OpenSearch's security plugin will let its own nodes talk to each other. Only production runs OpenSearch with TLS: docker-compose.prod.yml (layered on top of docker-compose.yml by deploy.sh) turns on the security plugin, mounts certs/opensearch/ into both nodes, and points the backend and worker at https://opensearch-node1:9200 with the root CA. Skip this only if certs/opensearch/ already contains a cert whose CN is opensearch-node1.

./scripts/generate_opensearch_certs.sh
# then add the printed root-ca.pem path to .env:
OPENSEARCH_CA_CERT=/home/ubuntu/cancerbot/certs/opensearch/root-ca.pem
Verify the CN if this ever looks wrong later openssl x509 -in certs/opensearch/node.pem -noout -subject — it must read CN=opensearch-node1. If it shows your public domain instead, the site's Let's Encrypt cert was copied into the wrong directory by mistake; regenerate with the script above.
07

Run deploy.sh

This is the only step that actually builds and starts the application. Everything before it is one-time host setup that deploy.sh doesn't (and shouldn't) do for you.

./scripts/deploy.sh

OpenSearch runs as a single node with a 512 MB heap, sized for a 4 GB server. Its indices are created with 0 replicas, so a healthy cluster reports green.

Running it directly as root (Hetzner's default login) is fine; npm then runs as root. When started with sudo from a normal user, npm runs as that user instead.

In order, it:

  1. Loads .env, checks for 10 GB free disk (running docker system prune -a if short), auto-fixes vm.max_map_count, and records the current images for rollback.
  2. Runs git reset --hard HEAD and git pull — if the pull changed deploy.sh itself, it re-executes the new version once.
  3. Builds the frontend on the host (npm install only when package-lock.json changed, then npm run build into client/dist).
  4. Builds the images with --pull and scans them with Trivy if it's installed.
  5. Backs up PostgreSQL (when it's already running), then starts the infrastructure with both compose files: both OpenSearch nodes, Dashboards, PostgreSQL and the NLP service.
  6. Waits for PostgreSQL, runs Alembic migrations (skipped when already at head), waits for OpenSearch, then runs the non-fatal seeds: seed_wikipedia_tags.py, backfill_chunks.py, backfill_source_metadata.py, backfill_conversation_titles.py.
  7. Starts the prod profile — Redis, the backend and the arq worker — and applies scripts/fix-iptables.sh so containers can reach Ollama on the host.
  8. Health-checks /health/ (rolling back to the previous images on failure), re-installs nginx.conf with this checkout's path as the web root and reloads nginx, and rotates old backups.
Local edits on the server are discarded Step 2 is a hard reset, so any uncommitted change to a tracked file on the server is lost on every deploy. Keep server-only settings in .env (untracked), never in tracked files.
Never run a production docker compose command without -f docker-compose.yml -f docker-compose.prod.yml — the base file alone starts OpenSearch without TLS or a password, and the backend then refuses to start. And never add --volumes to a prune: PostgreSQL and OpenSearch data live in named volumes.
First deploy on a fresh box If it fails partway through (health check timeout, a flaky step) after migrations already applied, the rollback logic now leaves the schema at wherever it reached instead of stepping it backward — safe to just fix the underlying problem and re-run.
08

Verify end to end

curl -sL http://localhost:8000/health
# expect: {"status":"ok","checks":{"database":{"status":"ok"},"ollama":{"status":"ok",...}},"status_code":200}

Then load https://cancer-bot.com in a browser and confirm the app itself renders, not just the health endpoint. Sign in once: the 6-digit code arriving by email proves Brevo and the worker are both working — without them nobody can log in.

09

Schedule the daily backup

scripts/daily_backup.sh dumps PostgreSQL and exports the OpenSearch indices into backups/ (keeping 7 days, optionally uploading to S3 or Google Drive). Unlike the app, it runs on the host, outside Docker — so it needs its own Python environment, pg_dump, and host-side addresses for the two databases. Nothing schedules it until you add the cron line below.

Install a Python environment and pg_dump

Ubuntu refuses a system-wide pip install (externally-managed-environment), so use a virtual environment. It needs requirements.txt too, because the OpenSearch export imports the app's own OpenSearch code. A newer pg_dump than the PostgreSQL 16 server is fine.

apt-get install -y python3-venv python3-full postgresql-client
python3 -m venv /root/cancerbot/.venv-backup
/root/cancerbot/.venv-backup/bin/pip install -r requirements.txt -r requirements-backup.txt

.venv-backup/ is git-ignored, and deploy.sh's git reset --hard leaves it alone. Rerun the pip install after a deploy that changes either requirements file.

Add the host-side addresses to .env

The compose files override these for the containers, so they only affect scripts run on the host:

POSTGRES_URL=postgresql://cancerbot:${POSTGRES_PASSWORD}@localhost:5432/cancerbot
OPENSEARCH_URL=https://localhost:9200
OPENSEARCH_CA_CERT=/root/cancerbot/certs/opensearch/root-ca.pem   # from Phase 6; its cert covers localhost
EMBED_MODEL_NAME=nomic-embed-text

Paste those lines exactly — ${POSTGRES_PASSWORD} is filled in from the same .env when the scripts load it, so the password isn't copied a second time. The OpenSearch password is likewise read from OPENSEARCH_INITIAL_ADMIN_PASSWORD (Phase 1). One catch: because the password ends up inside a URL, a POSTGRES_PASSWORD containing #, /, @, ? or % breaks it (backup_db.py then fails with "port could not be parsed"). Letters and digits are always safe.

Run it once, then schedule it

The script calls plain python3, so put the virtual environment first on the PATH:

PATH=/root/cancerbot/.venv-backup/bin:$PATH ./scripts/daily_backup.sh

When that ends with Backup complete, add it to crontab -e (02:00 server time, every day):

0 2 * * * PATH=/root/cancerbot/.venv-backup/bin:/usr/bin:/bin /root/cancerbot/scripts/daily_backup.sh >> /root/cancerbot/backups/cron.log 2>&1
Backups on the same disk aren't off-site Without BACKUP_S3_BUCKET or the Google Drive settings (see BACKUP.md), every copy lives on this server, and losing the server loses them too. Restores: scripts/restore_db.py for PostgreSQL, scripts/restore_opensearch.py for the indices (both in BACKUP.md).

Fixes already merged into the repo

Nothing to run for these — they're here so a future "why is this stuck?" moment doesn't repeat the same investigation. All three shipped as part of this same deploy.

deploy.sh — vm.max_map_count preflight + OpenSearch readiness wait

OpenSearch's bootstrap check requires vm.max_map_count ≥ 262144, which a fresh host doesn't have; and seeds used to run before OpenSearch was actually healthy, since only Postgres readiness was ever awaited.

scripts/deploy.sh
+ auto-fix vm.max_map_count via sysctl, verify, persist to /etc/sysctl.conf
+ wait up to 5 min for opensearch-node1's own healthcheck before running seeds

alembic — removed premature connection.commit() from two migrations

env.py runs a full upgrade heads batch in one transaction. A mid-migration connection.commit() in two data-migration files silently closed that transaction early — everything issued afterward, including every later migration in the same batch, landed in a fresh transaction that Alembic's own outer commit never touched, and got rolled back on connection close. The logs looked completely clean the whole time.

alembic/versions/cleanup_message_columns.py
- connection.commit()
print("[Migration] Cleaned up '?' from extracted_terms")
alembic/versions/populate_extracted_terms.py
- connection.commit()
print(f"[Migration] Successfully populated {processed} messages\n")

This is exactly why a fresh server's DB got stuck at populate_extracted_terms_001 — many revisions behind head — despite alembic upgrade heads appearing to run cleanly through every step, every time.

deploy.sh — rollback no longer downgrades schema on a first-ever deploy

The rollback path fell back to alembic downgrade -1 whenever migrations had run but no backup existed yet — true by definition on a first deploy, since the backup step needs Postgres already running from a previous attempt. On a first deploy there's no old backend image whose compatibility that protects; it only strands the schema behind head. Several failed attempts during initial setup compounded this into the exact bug above.

scripts/deploy.sh
elif [ "$MIGRATIONS_APPLIED" = true ] && [ "$FIRST_DEPLOY" = false ]; then
_alembic alembic downgrade -1 ...
+ elif [ "$MIGRATIONS_APPLIED" = true ] && [ "$FIRST_DEPLOY" = true ]; then
+ echo "leaving schema as migrated rather than downgrading"
