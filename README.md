# CancerBot

A retrieval-augmented generation (RAG) chatbot that answers cancer-related questions from published medical literature, with every claim cited back to its source (PubMed, CrossRef, ClinicalTrials.gov, Wikipedia).

> **Medical disclaimer.** CancerBot is an information tool, not a medical device. Its answers are generated by a language model from retrieved literature and can be incomplete or wrong. Nothing it says is medical advice — always discuss diagnosis and treatment decisions with a qualified clinician.

## How it works

For every message:

1. **Extract terms.** An NLP service (scispaCy) pulls biomedical entities out of the question and expands them with MeSH synonyms.
2. **Search live.** PubMed, CrossRef, Wikipedia and ClinicalTrials.gov are queried in parallel with those terms.
3. **Index.** New results are chunked, embedded with `nomic-embed-text` (Ollama), and added to OpenSearch. The corpus grows with use; there is no offline ingestion step.
4. **Retrieve.** A hybrid search runs dense (vector) and lexical (BM25) queries, fuses them with Reciprocal Rank Fusion, keeps only sources above a cosine-similarity floor, and reorders them with a cross-encoder.
5. **Generate.** An LLM writes a streamed answer citing `[source1]`, `[source2]`…, which are rewritten to stable IDs such as `pmid:12345`. Providers are tried in order: a local Ollama model (only if `OLLAMA_GEN_MODEL` is set), then Groq (`openai/gpt-oss-120b`), then Gemini.

Users can optionally save a health profile (cancer type, stage, biomarkers, age band, treatment status) to frame answers. Questions about the profile itself ("what stage did I save?") are answered directly from it, without any model generation.

Other features: email-verified accounts, shareable read-only conversation links, conversation export (Markdown / print-to-PDF), clinical-trial finder, asking follow-up questions about a specific cited source, answer feedback, and an admin console.

## Stack

| Component | Technology | Port |
|---|---|---|
| API | FastAPI (REST + WebSocket streaming) | 8000 |
| Frontend | React 19 + Vite + MUI | 5173 |
| Search | OpenSearch 3 (2 nodes) — BM25 + k-NN | 9200 |
| Database | PostgreSQL + Alembic | 5432 |
| NLP service | scispaCy `en_core_sci_sm` + cross-encoder reranker | 8100 |
| Embeddings | Ollama `nomic-embed-text` (runs natively) | 11434 |
| Generation | Optional local Ollama model, then Groq, then Gemini | — |
| Background jobs | arq + Redis (emails, scheduled deletions, cleanup) | 6379 |
| Email | Brevo | — |

## Running locally

### Prerequisites

- Python 3.12
- Node.js 20.19+ (Vite 8)
- Docker + Docker Compose
- [Ollama](https://ollama.com), installed natively (on a Mac, Docker can't use the Metal GPU)
- A [Groq API key](https://console.groq.com) (a Gemini key is optional, for fallback) — or a local Ollama model instead (see below)

### 1. Configure

```bash
cp example.env .env
```

At minimum, set `OPENSEARCH_INITIAL_ADMIN_PASSWORD`, `POSTGRES_PASSWORD`, `JWT_SECRET` and `GROQ_API_KEY`. Generate a JWT secret with:

```bash
python3 -c "import secrets; print(secrets.token_hex(32))"
```

`example.env` documents every variable. Keep `ENV=development` locally.

**Running without cloud LLMs.** Pull a chat model (`ollama pull llama3.1:8b`) and set `OLLAMA_GEN_MODEL=llama3.1:8b`. Every LLM call then tries it first, falling back to Groq and then Gemini only if it fails; with no `GROQ_API_KEY` set, Groq is simply skipped. Expect weaker answers than with Groq: the prompts and citation rules are tuned for `openai/gpt-oss-120b`, and small local models follow them less reliably.

### 2. Start services

```bash
docker compose up -d          # OpenSearch, Dashboards, PostgreSQL, NLP service
ollama serve &
ollama pull nomic-embed-text
```

The first NLP-service build downloads the scispaCy model and can take a few minutes.

### 3. Backend

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
alembic upgrade head
uvicorn src.main:app --reload
```

### 4. Frontend

```bash
cd client
npm install
npm run dev
```

Open http://localhost:5173.

**Skipping emails locally.** No email is sent outside production. Set `DEV_EMAIL_SHORTCUTS=true` in your `.env` and registration creates an already-verified account, and "Forgot password" goes straight to the set-new-password page. It's refused when `ENV=production`, and the test suites run with it off. Without it, the `POST /auth/register/` response includes a `verification_token` (visible in your browser's network tab); open `http://localhost:5173/verify-email?token=<token>` to verify.

**Background jobs (optional locally).** Emails and scheduled account deletions run in the arq worker, which needs Redis. Without them the app still works; queued jobs are logged and skipped. To run them, start Redis (`docker compose --profile prod up -d redis`) and then the worker (`arq src.worker.WorkerSettings`).

### Production

`docker compose --profile prod up --build` adds the backend, worker and Redis containers. `scripts/deploy.sh` is the full deploy (image build, Trivy scan, migrations, health check, nginx reload). See [DEPLOY_EC2.md](DEPLOY_EC2.md), [DEPLOY_ORACLE_CLOUD.md](DEPLOY_ORACLE_CLOUD.md) and [BACKUP.md](BACKUP.md). Set `ENV=production` (outside production, token-issuing endpoints return their tokens in the response for test automation) and `FRONTEND_URL` to your public origin; the backend refuses to start in production without it.

## Tests

```bash
pytest                    # backend (no services needed)
cd client && npm test     # frontend
```

The NLP service and Playwright end-to-end suites are covered in [TESTING.md](TESTING.md). CI runs the backend, NLP service and frontend suites on every push and pull request.
